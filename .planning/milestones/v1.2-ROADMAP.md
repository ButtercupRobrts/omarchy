# Milestone v1.2: Target-Size Transcode

**Status:** ✅ SHIPPED 2026-09-18
**Phases:** 8-9
**Total Plans:** 2

## Overview

Milestone v1.2 inverted v1.1's estimate→actual loop: the user names a target output size and `omarchy-transcode` derives the best parameters that fit. Phase 8 shipped `omarchy transcode <video> mp4 <res> --target <size>` — free-text size parsing (`25M`, `1.5G`, `500K`, `25MB`, bare `25` = MB) into integer bytes, video bitrate derived from probed duration minus the 192k audio term, resolution auto-step-down across locked floor rungs (4k → 1080p → 720p), two-pass encoding with per-run `mktemp` passlogs, a single overshoot retry, and honest refusal naming the achievable minimum below every floor — all validated before menus and the start notification. Phase 9 layered a `Custom size…` sentinel row onto the mp4 quality menu that prompts via `omarchy-menu-input` and routes through the identical parser/planner/encoder — interactive and CLI runs produce byte-identical ffmpeg argv.

## Milestone Summary

**Key Decisions:**

- Single pipeline for both entry points: the Custom row mints a `target:<bytes>` sentinel that `main()` unwraps into the exact `--target` variables — interactive ≡ CLI byte-identical by construction
- Honest refusals over silent degradation: below every floor, the run refuses naming the achievable minimum rather than produce a worse file; a ≥source target redirects to the quality path
- Planner refusals are terminal in the interactive flow too (D-01) — the re-prompt budget is for typos, not for retrying past a floor the user needs to absorb
- Two-pass + one bounded retry, never a convergence loop — the done notification reports the actual size either way; honest hit/miss is the point
- Decimal (SI) units for all user-facing sizes — `25M` means 25,000,000 bytes, matching file managers and upload limits like Discord's 25 MB cap (switched post-UAT when the IEC mismatch surfaced as ~16 MB of apparent overshoot)

**Issues Resolved:**

- EXIT trap can't see function-`local` passdir under errexit → path baked via `printf %q` into the trap string (caught by the harness)
- Pass-2/2 replacement toast could abort the encode under `set -e` if the notification daemon failed → `|| true` (06ad1096, WR-01)
- Random `mktemp` passdirs made byte-identical argv pins unsatisfiable → `sed` normalization before `cmp`
- Forged gif pick could mint `target:` into a `.gif` filename → sentinel branch format-gated on mp4 (79928688, WR-01)
- IEC/MiB vs decimal-MB unit mismatch surfaced in dogfood (file showed ~16 MB over the entered target) → all parse/token/label sites switched to SI (4d422ffe)

**Issues Deferred:**

- `192k` audio constant across 5 sites; `(rate)×duration×125` formula shared by `estimate_label`/`min_label` — extraction deferred until the PR #12135 review window closes (IN-04/IN-05)
- Retry `mv -f` TOCTOU — accepted risk class, inherent to check-then-move (IN-06)
- `--target` + positional-menu gif wastes one resolution prompt before refusing — locked check-site ordering (IN-05)
- Mint-guard `return 1` vs flag-arm `return 2` — unreachable cosmetic inconsistency (IN-02)
- Stub pass-2 arm `out=` ordering fidelity — test-harness nicety (IN-04/08)

**Close-out:**

- UAT: Phase 8 refusal verified live (`--target 10M` → "smallest achievable ~384 MB"); Phase 9 Custom-row dogfood passed (`400M` → output at/under 400 decimal MB in Files)
- Security: both phases threat-secure at ASVS L1 — 10/10 register threats closed (5 per phase)
- Stacked upstream branch carved: `feat/transcode-target-size-upstream` (5 code-only commits on the v1.1 PR branch, awaiting PR #12135 resolution)
